# 大数分解算法调研报告

> 配套文档，对应《产品需求设计-ZCode-GLM5.3Flash-v1.8.md》FR-20。
> 面向读者：想理解本工具"为什么这么算、算不动时为什么不继续"的人。

---

## 1. 先说结论

大数分解（整数分解）是**计算困难问题**：目前没有已知的多项式时间（经典计算机）算法能分解任意大整数。
RSA 公钥密码体系的安全性就建立在这个困难性上。

因此本工具的设计立场是：

1. **能判定的就如实判定**——质数（素性）在数学上是**可判定**的，Miller-Rabin 可以在极短时间内以
   极高置信度（或对小整数确定性）给出结论；
2. **能分解的就完整分解**——试除、p-1、rho、ECM 各有各的"甜蜜区"；
3. **分解不动就如实说分解不动**——绝不把"没找到因子"包装成"这是质数"。
   剩余部分可能是质数，也可能是两个大质数的乘积，界面上原样标注。

## 2. 算法对比

| 算法 | 复杂度（大致） | 甜蜜区（被分解数的规模） | 内存 | 并行性 | 备注 |
|---|---|---|---|---|---|
| **试除（Trial Division）** | O(π(B) · M(n)) | 找出 < 10 万的小因子 | O(1) | 易 | 本工具第一道工序，必做 |
| **Fermat 平方差** | 取决于因子间距 | 两个因子大小接近时奇效 | O(1) | 易 | 通用性差，本工具未启用 |
| **Pollard rho** | O(p^½)，p 为最小因子 | ≤ 10^20 左右的中小因子 | O(1) | 易（不同起点） | **随机算法**，耗时方差极大 |
| **Pollard p−1** | O(B·M(n)) | 当 p−1 是"平滑数"（只含小因子）时秒杀 | O(1) | 中 | 第一阶段 B1=50000 |
| **Pollard p+1** | 同 p−1 | 当 p+1 平滑时 | O(1) | 中 | 本工具未启用（收益/成本比低） |
| **ECM（椭圆曲线）** | 期望 O(exp(√(2 ln p · ln ln p))) | 找 20~40 位因子最优 | O(1) | **极佳**（曲线之间完全独立） | 本工具为**演示级**实现 |
| **QS（二次筛）** | O(exp(√(ln n · ln ln n))) | 50~110 位 | 大（GB 级） | 中 | 需大量内存与工程优化 |
| **GNFS（数域筛）** | O(exp(1.9 (ln n)^⅓ (ln ln n)^⅔)) | 110 位以上 | 极大（TB 级） | 难（需集群） | 当前公开纪录的算法 |

> M(n) 表示 n 位数的乘法代价。p 指待找出的那个因子。

**一句话选型逻辑**：因子越小越好找；因子越大，需要从"运气型算法"（rho）升级到"结构型算法"（ECM），
再到"重型武器"（QS/GNFS）。重型武器需要专门的大工程（yafu、msieve、cado-nfs），
超出了"纯标准库单文件工具 + 实时可视化"的目标，本工具不实现。

## 3. 本工具的实际执行顺序

对一个待检查的数 n，按序进行，任一步得出最终结论就停止：

```
1. 试除
   └─ 用 10 万以内的 9592 个素数逐个试除（位数很大时自适应减少个数）
      ├─ 全部除尽  → 合数，给出完整质因数分解（如 2^12 × 5^12）
      └─ 有剩余 m  → 进入第 2 步

2. Miller-Rabin 素性检测（对剩余部分 m）
   ├─ n < 3.317×10^24：用前 12 个素数作底数，结论**确定性正确**
   ├─ 更大的数：按位数用 36→3 个底数，错误概率约 4^(−底数个数)
   └─ 位数 > 8000：不判定（Miller-Rabin 本身太慢），如实标注

3. 若 m 确定是合数 → 找它的一个非平凡因子
   ├─ 自动（默认）  ：Pollard p−1（B1=50000）→ Pollard rho（Brent 变体）
   ├─ 仅 rho        ：只跑 rho
   ├─ 仅 p−1        ：只跑 p−1
   ├─ ECM 椭圆曲线  ：Montgomery 曲线、第一阶段 B1=2000、最多 30 条曲线
   └─ 深度 p−1→ECM→rho：三者的深度组合（较慢但覆盖更广）

4. 找到因子 d → 递归分解 d 与 m/d（完整模式）
   或只给出 n = d × (n/d)（两数相乘模式）

5. 找不到 → 如实标注：
   "剩余部分可能是质数，也可能是两个大质数的乘积"（橙色）
   "所选算法未能分解，可换其它算法"（橙色）
```

### 3.1 为什么先试除而不是直接 Miller-Rabin？

试除能一次性解决绝大多数"平凡"情况（偶数、5 的倍数、小因子连乘），代价极低。
直接对一个含小因子的合数跑 Miller-Rabin 会白白做几十次大数模幂。

### 3.2 为什么要自适应减少试除素数个数？

试除的代价 ≈ 素数个数 × 数字位数。对一个 20 万位的数做 9592 次取模，
光试除就要几秒——而它大概率一无所获（因为大数的小因子早就被前面的步骤发现了）。
本工具按位数递减试除规模（60 位以内全量 9592 个，20 万位以上只试前 100 个），
把时间留给真正有机会出结果的算法。

### 3.3 位数上限与"降级"

| 阶段 | 位数上限 | 超限时的行为 |
|---|---|---|
| Miller-Rabin | 8000 位 | 不判定，标注"位数过大未能判定" |
| Pollard p−1 | 2500 位 | 跳过该算法 |
| Pollard rho | 8000 位 | 跳过该算法 |
| ECM（演示级） | 4000 位 | 跳过该算法 |

这些上限不是"数学上不能算"，而是"在交互式工具里继续算没有意义"：
一次 rho 迭代要对一个 8000 位的数做模乘，单次迭代就是毫秒级，
找到一个 4000 位大小的因子需要约 10^2000 次迭代——宇宙寿命都不够。
与其假装在算，不如停下来如实告诉用户。

## 4. ECM 为什么是"演示级"

完整的 ECM 实现（GMP-ECM 级别）包含：

- 第一阶段（Stage 1）：按 B1 做点乘， Montgomery 曲线 + 齐次坐标；
- 第二阶段（Stage 2）：Standard continuation / FFT continuation，把搜索范围扩展到 B2 ≈ 100×B1；
- Suyama 参数化、PRAC 点乘、模乘的 Montgomery 表示（不用除法）；
- 数百到数万条曲线，按 B1 递增的 multi-curve 调度。

本工具只实现了**第一阶段 + Montgomery 曲线仿射/投影坐标 + Suyama 参数化 + 30 条曲线上限，B1=2000**，
纯 Python、无 GMP。这足以分解十几到二十几位的因子，用于演示 ECM 的工作原理，
但与真正的 ECM 能力差距在数量级上。若需真正的 ECM，请用 GMP-ECM。

## 5. 并行模型：为什么"1 个数量级 = 1 个进程"

本任务的并行单位是**数量级（组）**，不是"单个数"：

- 每个数量级要顺序地从 10^k 往上检查，天然是串行的；
- 不同数量级之间完全独立，无需通信；
- 单个数分解的耗时方差极大（rho 是随机算法），按数切分会造成严重的负载不均；
- 按组切分时，进程数 = 并行组数，调度简单、内存可控、状态清晰（便于暂停/跳过/显示进度）。

结果通过 `result_q` 回传，携带序号 `seq`，界面侧按序号缓冲后**顺序上屏**，
乱序完成不影响阅读顺序。

### 5.1 "49 个进程跑不满 48 核"的结构性原因

如果观察到开了 N+1 个进程、机器有 N 个逻辑核心，但整体 CPU 占用率达不到 100%，
常见原因有这些（按贡献排序）：

1. **任务数 < 进程数**：滑动窗口只在有任务时才提交。若只剩 2 个组在跑，
   剩下 47 个进程是空转的（本工具在资源栏区分显示"忙碌/空闲"进程数）。
2. **尾部效应**：流水线收尾时只剩最后几个长任务，其余进程已经退出——
   这是"Amdahl 定律 + 任务粒度不均"的必然结果，不是 bug。
3. **GIL 不存在，但 GMP 也不存在**：Python 大整数运算是纯 C 实现、不持 GIL 竞争，
   但比 GMP 慢 3~10 倍；单进程内部的模乘序列无法再并行。
4. **内存带宽 / 缓存**：大数运算是内存带宽密集型，48 个进程同时搬几百 KB 的
   大整数会撞上内存带宽墙，导致"CPU 占用 100% 但吞吐不线性增长"。
5. **spawn 启动开销**：Windows 上每个进程冷启动要重新导入解释器与模块（约 0.2~0.5 秒），
   短任务场景下这部分时间也不产生计算吞吐。
6. **主进程是单点**：所有消息都要经过 `result_q` 回到主进程再做格式化与渲染。
   消息限速（试除 10 条/秒、阶段 1 条/秒）正是为了不让主进程成为瓶颈。

**结论**：这是" embarrassingly parallel 但粒度不均 + 内存带宽受限"的典型形态，
属于结构性问题；本工具通过进度面板与资源监控把它**如实显示出来**，而不是掩盖它。

## 6. 复杂度与"多久能找到 3 个质数"

由素数定理，10^k 附近随机一个数是质数的概率约为 1/(k·ln10) ≈ 1/(2.303·k)。
因此找满 3 个质数平均需要检查约 **3 × 2.303 × k ≈ 6.9·k** 个数……

更精确一点（从 10^k 起顺序扫描，质数间隔的期望约为 k·ln10 ≈ 2.303·k）：
找满 3 个质数平均需要检查约 **2.3·k × 3 ≈ 6.9·k** 个数。

实践观测（本工具）：

| 数量级 | 平均需检查 | 每数耗时 | 单组大致耗时 |
|---|---|---|---|
| 10^12 | ~28 个 | < 1 ms | < 0.1 秒 |
| 10^30 | ~70 个 | ~1 ms | < 1 秒 |
| 10^100 | ~230 个 | ~10 ms | 数秒 |
| 10^300 | ~690 个 | ~0.2 秒 | 2~3 分钟 |
| 10^1000 | ~2300 个 | ~3 秒 | 数小时 |

所以"每组限时"是必需的功能：把不可控的长尾任务切成可控的片段。
