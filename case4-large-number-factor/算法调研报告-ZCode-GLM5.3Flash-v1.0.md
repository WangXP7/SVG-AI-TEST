# 大数（合数）分解算法调研报告

> 配套项目：大数分解可视化工具（factor_gui.py / 大数分解工具.exe）
> 日期：2026-08-30 ｜ 本文同时回答用户问题："49 个软件进程，为什么 CPU 跑不满？"

---

## 1. 问题背景

把大合数 n 分解为素数之积，是计算复杂性意义上的困难问题。目前学术界与工程界的共识：

| n 的规模 | 可行性 |
|---|---|
| ≤ 2^64（约 20 位） | 任何现代方法都轻松 |
| 60~80 位 | 需要 ECM/QS，分钟~小时级 |
| RSA-100（100 位） | QS 时代里程碑；现数小时~天 |
| RSA-155（512 位） | 1999 年 GNFS，约 8 个月（数百台机器） |
| RSA-250（829 位） | 2020 年 GNFS，约 2700 核·年 |
| RSA-2048 及以上 | 远超人类现有算力（可信几十年内不可行） |

**关键规律**：没有一个算法能"高效分解任意大数"。不同算法各有擅长的因子规模，
实际工程（如 YAFU、CADO-NFS）都是多算法流水线 + 海量算力。

---

## 2. 主要算法对比

| 算法 | 复杂度（找因子 p / 分解 n） | 擅长规模 | 内存 | 可并行性 | 本程序 |
|---|---|---|---|---|---|
| 试除法 | O(√n) | 因子 < 10^5~10^6 | O(1) | 差 | ✅ 预处理（10 万内素数表） |
| Fermat 法 | O(√n)（p、q 接近时快） | p≈q 的特殊半素数 | O(1) | 差 | ⬜（场景太窄） |
| Pollard rho (Brent) | O(p^(1/2)) ≈ O(n^(1/4)) 期望 | 因子 ≤ 15~20 位 | O(1) | 可多实例（不同参数） | ✅ |
| Pollard p-1 | p-1 光滑时极快；否则无效 | p-1 为 B-光滑 | O(1) | 差（单序列） | ✅（B1=50000 一阶段） |
| Williams p+1 | 同上，基于 p+1 光滑 | 同上 | O(1) | 差 | ⬜（与 p-1 触发面重叠） |
| **ECM（椭圆曲线）** | exp(√(2 ln p · ln ln p))——**只取决于因子 p** | 15~60 位因子最有效 | 每曲线 O(1) | **极好：曲线间天然并行** | ✅（纯 Python 演示级，B1=2000、30 曲线） |
| 二次筛 QS / MPQS / SIQS | exp((1+o(1))√(ln n · ln ln n)) | 60~100 位合数 | 数百 MB~GB | 筛段可并行，矩阵难并行 | ⬜（实现复杂，纯 Python 无竞争力） |
| 数域筛 GNFS | exp((1.92+o(1)) (ln n)^(1/3) (ln ln n)^(2/3)) | >100 位（世界纪录级） | GB~TB | 分工可并行，工程量巨大 | ⬜（应使用 CADO-NFS 等成熟实现） |
| 特殊数域筛 SNFS | 比 GNFS 低若干指数因子 | 有特殊代数形式的数 | 大 | 同上 | ⬜ |

实用工具对照：GMP-ECM（ECM/p-1/p+1 的工业实现）、YAFU（自动多算法流水线）、
msieve（QS/GNFS）、CADO-NFS（开源 GNFS）。**若目标是"尽可能分解大数"，
正确路径是把本程序的前端接到这些工具上，而不是用纯 Python 重写它们。**

## 3. 本程序的算法组合（用户可选）

在「找因子算法」下拉框中选择，作用于每个数的试除之后：

| 选项 | 流程 | 适用场景 |
|---|---|---|
| 自动（p-1 → rho）【默认】 | 先 p-1 碰运气，再 rho 兜底 | 日常使用，平均最快 |
| 仅 Pollard rho | 只用 rho | 观察随机算法行为 |
| 仅 p-1 | 只用 p-1，找不到就放弃该数（标橙） | 验证 p-1 光滑性假设 |
| ECM 椭圆曲线 | 只用 ECM（B1=2000，≤30 条曲线） | 中等大小因子；注意纯 Python 版速度有限 |
| 深度 p-1 → ECM → rho | 三级流水，最全面 | 不限时长时间挂机 |

实现说明：ECM 采用 Montgomery 曲线的仿射坐标简化实现（Suyama 参数化 → 随机曲线 →
第一阶段标量乘 → 模逆失败即得到 gcd 因子）。**这是教学演示级实现**：
工业级 ECM（GMP-ECM）使用 Montgomery 阶梯（免求逆）、二阶段、大素数步长优化，
速度高出多个数量级。

## 4. 为什么 48 线程 + 49 个进程，CPU 却跑不满？（重点分析）

现象：任务管理器里程序有 49 个进程，但"本程序 CPU ≈5 核（11%）"，整机占用也不高。
逐层排查后的结论如下（按影响从大到小）：

### 4.1 主因：49 个进程里，"有活干"的只有几个
本程序的并行模型是 **1 个数量级 = 1 个任务 = 1 个计算进程**（滑动窗口派发）。
进程数是"上限"，真正决定 CPU 占用的是"进行中的任务数"：

- 例如输入 10^50（51 个数量级）：前面 40 多个小数量级几分钟就完成了，
  只剩 10^44~10^49 这几个"难组"（它们的 10^k+1 常是难分解的合数，陷在随机算法里）。
- 此时 49 个进程中 **只有 5 个进程各自领着一个难组在算**，其余 44 个进程阻塞在
  任务队列的 `get()` 上等待派发——它们不消耗 CPU。
- 监控栏的"CPU ≈5.2 核（11%）"与"5 个难组"精确对应，不是 bug，是任务耗尽了。
- 界面已做的改进：资源栏区分"忙碌 X · 空闲 Y"，进度区每行标注该组占用的进程号，
  一眼可以看出谁在干活、谁在等待。

### 4.2 次因：每个难组是单线程算法，1 组最多吃满 1 核
rho、p-1、ECM（本实现）都是**串行算法**：一个数在一个进程里只能用一个核。
要给一个难组提速，得在算法内部并行：

- ECM 天然可并行（不同曲线互不依赖）→ 工业实现正是这么做的；
  本程序目前每条曲线仍由同一个进程顺序尝试，后续可改为"曲线池"分发到多个进程。
- rho 也可多实例并发（不同 c 参数），但收益随核数递减。

### 4.3 三因：Python 解释器开销
即使"忙碌"的进程，也不是每一纳秒都在做有效数学运算：

- 试除的 9592 次模除、rho 的每一步，都夹着 Python 字节码循环开销；
  纯 Python 的大数乘法虽是 C 实现，但解释器开销使有效算力远低于 GMP/ C 语言实现
  （同类运算 GMP-ECM 可快 50~200 倍）。
- 所以"1 个忙碌进程 ≈ 1 个核的 100%"在 OS 看来成立，但**单位时间完成的搜索量**
  远低于同核数的 C 程序。

### 4.4 四因：进程启动与通信的固定开销
- spawn 48 个进程各自要解释器冷启动 + 重建素数表（首次约 2~5 秒）；
- 任务/结果经过 mp.Queue 序列化传输，小任务的通信开销可与其计算量同数量级
  （这就是为什么 10^12 这类"太容易"的输入并行后反而比串行慢）。

### 4.5 结论与建议
1. **跑不满是"任务太少、太难"的结构性结果，不是调度故障**：进程数是上限，
   忙碌数=进行中组数；难组单线程算法只能吃 1 核。
2. 想让 48 核跑满，可选：
   - 用「不限时」同时输入**更大的 N**（数量级多，任务管够）；
   - 对剩余难组使用 ECM 并把"曲线池"并行化（列入选做方向）；
   - 把找因子阶段外接 GMP-ECM/YAFU（工程上最有效，列入 backlog）。
3. 监控口径已细化：资源栏区分忙碌/空闲进程，进度行给出每组的进程号与 CPU%，
   与本文分析一一对应。
